海洋能源智库｜Mp2RSS 订阅管理改造开发文档

V1.0 · 2026-10-11 · 状态：开发设计与代码核查完成，付费账号联调待开展。本次只编制方案，未更换生产采集源，未调用付费账号接口，未执行远端订阅增删。

建议采用“Mp2RSS Open API 为主、RSS 为备用”的接入方式。保留现有文章库、分类、向量检索和智库证据体系；将旧公众号扫码采集替换为供应商连接器。公众号、X 推文、X 长文共用订阅管理入口，但分别解析和保存出处。

证据边界：已阅读官方 API、FAQ、订阅管理、快速开始和会员说明；已检查当前工作区代码，并只读确认线上存在 pipeline-worker.mjs 和自动提取模块。未取得 Feed 密钥及真实付费响应，全文完整率、历史覆盖、嵌套作者字段和实际稳定性均待联调。文中“建议、拟新增”为待开发项，不能视作已上线功能。

1. 先明确 X 推文、长文与订阅的关系

内容类型本系统如何理解建议呈现与分析
公众号文章一个公众号下的文章内容流文章标题、原文、中文摘要、作者、发布时间和微信公众号原链接
X 推文 posts账号发布的帖子；可能带媒体、转推、引用或线程短内容也可作为线索；没有标题时生成标记为“展示标题”的摘要，不能伪称原文标题
X 长文 articles同一 X 账号的另一种内容流独立文章详情，保留标题、正文完整性及长文原链接
X 线程 thread推文流中的系列帖子，不能直接当成长文流保存每段的作者/时间/帖子标识；信息缺失则明确标注，不推测补齐
转推／引用传播动作与被传播内容是两个层次外层账号不自动成为内层内容的作者；“转推”不能生成“投资、合作”等产业关系

按官方订阅模型，X 订阅单位是账号，同一账号分别读取 posts 和 articles；不应把它设计成两个独立付费账号名额。公众号与 X 共用套餐配额。X 账号新增、搜索、取消在供应商 Web 控制台完成，本系统导入已订阅账号并提供两条内容流的本地开关。若实购套餐另有约定，以账户实际权益为准。

依据：官方订阅管理

官方 FAQ 明确：首次订阅不回溯历史，只收录订阅后的新内容；源站发布到服务收录平均约需 2—3 小时，并非实时保证。因此原公众号历史库必须保留；“同步近三天”只能同步供应商已经持有的资料，不能承诺把订阅前三天补齐。长文列表为空也可能只是账号没有发布长文，不能直接报采集失败。

依据：官方 FAQ（历史范围、内容类型与更新延迟）

线上只读检查显示最近记录的综合任务包含 pipeline-worker.mjs，结果为 partial。该事实说明自动处理模块已存在，不证明每条文章均已处理成功。本方案以当前代码为依据，不沿用此前“只有翻译、没有自动提取”的旧结论；迁移验收时另核查失败明细。

3. 接入架构：平台、供应商、内容流分开

建议结构：供应商账户 → 平台账号映射 → 内容流 → 原始收录记录／版本 → 原版文章库 → 幂等投递 → 智库文档与处理任务 → 证据、地图、检索和研究。Mp2RSS 是传输供应商；微信公众号或 X 才是原始发布平台；具体账号才是发布者。

层次建议职责关键约束
ProviderAccount保管 Mp2RSS 密钥、连接状态和人工登记到期日不在浏览器或文档中存真实密钥；到期日无已确认公开接口时不可伪造自动读取
SourceBinding关联现有 sources 与供应商账号 ID旧 fakeid 与新 mpId 为不同命名空间；人工核对迁移映射，不凭同名自动合并
Stream公众号文章／X 推文／X 长文三种流独立进度X 两条流共享账号，但有各自水位、失败状态及开关
RawItem + Version保存响应正文、原文 URL、内容哈希及获取时间原始响应不包含认证头或带密钥请求 URL；正文原文与译文分开
Outbox + ProcessingJob文章入库后可靠投递，按版本处理同一事务写入文章及 outbox；重复投递不重复建事件；失败可重试
智库存储规范化文档驱动现有分析和展示public.articles 与 ocean_intel 不是同一存储；原版入库成功不等于智库已可查

不建议仅将合集 RSS 加入旧页面后宣布完成接入：合集可能让多个发布者被归入同一个 source，且渲染后的 Feed 会弱化 X 转推、引用和线程的结构。API 作为主路径更适合溯源；备用 Feed 需要独立标记来源和内容完整性。

4. 供应商 API 契约摘要与待验证边界

官方 API 使用 Feed 密钥作 Bearer 凭据，服务地址为 https://mp2rss.bugcode.dev。以下只列实现必需的调用；具体字段与未来变动以官方契约和联调样本为准。

用途方法与路径分页／处理要点
发现已订阅账号GET /open-api/subscriptionssourceType 区分 mp／x；每页最多 50
添加／取消公众号POST /open-api/subscriptions；DELETE /open-api/subscriptions/{mpId}添加提交 articleUrl；成功写操作为 204，不解析 JSON
公众号内容GET /open-api/subscriptions/{mpId}/articles每页最多 100；没有 total，按不足一页结束
X 推文GET /open-api/x/{xUserId}/posts每页最多 50；使用 postId，保留嵌套结构
X 长文GET /open-api/x/{xUserId}/articles每页最多 50；以原始 url 标识，正文可能为空

时间为 UTC 毫秒，存储统一 UTC，前端显示北京时间。公众号正文也可能为空；X 用户 ID 必须按字符串保存。429 按 Retry-After 退避；401、403、404 分别进入凭据、权益或订阅核查流程，不反复盲重试。

依据：Mp2RSS Open API 契约

尚未实测的边界：第三方是否覆盖所有帖子类型及编辑；转推对象/线程内部是否总有作者、ID、日期；长文 URL 是否保持稳定；正文空值何时补齐；旧资料保留多久；帖子原链接可否由返回身份稳定定位；分页时新增条目的漂移表现。这些均列入首轮付费样本验证，不能凭示例响应承诺。

文档服务介绍页对 X API 能力有概括性表述，与具体 API/FAQ 的明确限制不完全一致；实现以详细 API 和 FAQ 为准，不开发未公开的 X 搜索、订阅写接口，不抓取控制台内部接口冒充 Open API。

6. 增量同步、修订与去重规则

以下频率是本项目建议，不是供应商 SLA：内容流默认每 30 分钟轮询，任务加随机错峰；订阅名单每日核对一次，并提供“立即刷新”。首次只处理供应商可提供的近三天资料，用户可选择其可用历史全量。过短轮询不会消除供应商本身的收录延迟。

场景建议规则完成条件
首次同步逐源分页读取，先持久化再推进进度；有效范围写入覆盖说明不会因空列表或账户刚订阅而显示“全历史同步完成”
后续增量重读首页并覆盖最近七天，结合稳定 ID＋哈希去重；周度核对可用旧记录覆盖延迟收录及正文补齐；老记录改动不得只靠发布时间水位发现
分页漂移本轮保存开始水位；连续边界重叠并回扫首页；中断可重放并发新帖造成页码位移时不丢数据；不要承诺无快照接口下的绝对一致性
正文为空存元数据并标 pending_body；单独延迟复查无正文不生成全文向量、强事实关系或“全文已处理”状态
短推文短文本可独立为完整推文，不套用文章最小长度门槛“短而完整”与“仅长文摘要”分别判断
正文修订版本哈希变化后生成新版本，重新分类／抽取／翻译／向量化旧研究保留所引版本；未更新资料不重复消耗模型调用
跨渠道重复外部身份优先；精确原文 URL 辅助；内容近似仅聚合不删除出处同一文章旧库与新供应商记录合并溯源，不丢来源证据
X 两条流重复按内容类型＋稳定标识区分；推文引用长文建立“指向”关系不因标题相似自动把两种内容合成同一条原文
失败与恢复单源失败隔离；账号失效暂停受影响任务；续费后从可用水位恢复漏采时间范围可见；不能承诺补回供应商未收录的断档
删除／失效供应商列表中消失不自动推断源文删除保留历史证据；原链不可用时单独标注可访问性

正文、媒体和外链分别处理：首期保存媒体 URL 与类型，不默认下载视频，不声称读取图片文字。需要 OCR／视频转写时单独建任务、标明证据介质。抓取外链不得覆盖原帖子；禁止将付费凭据发送给外链域名。

7. 接入现有 AI 与证据处理流程

建议处理依赖：规范化原文 → 正文完整性／语言／主题初筛 → 原文抽取与中文翻译 → 证据校验、主题复核 → 向量与检索索引 → 智库发布。抽取应以原文为依据，翻译不必强制先于抽取；当前 pipeline-worker 先抽取后翻译可以继续复用。

处理阶段必须满足的行为输出状态
主题过滤围绕海洋油气、海上风电、海洋能、海工装备、海底 CCS 与相关运输政策；宽泛能源内容需有海洋关联accepted／rejected／needs_review；短帖上下文不足时待复核，不直接丢弃
抽取复用 auto-extract，输出实体、事件、关系、指标；先验证来自哪一层帖子四类可为空；“零条关系”不等于失败；不得把账号认证当事实认证
翻译中文原文跳过；外文保留原文＋中文；名称、单位、预测和引述忠实保留独立 translation 状态，不让摘要成功掩盖正文失败
引用校验片段必须来自指定版本及指定作者段落；校验 ID、位置、数值、单位校验通过只说明有文本依据，仍为待核验主张
指标归档区分实际、计划、预测、设计能力；区分发布日期与统计期指标来源可追溯；多条新闻数字不能直接拼为同口径趋势
向量化按原文／译文版本及模型签名建索引；长文切片，不静默截断只有当前版本完成才标 ready；不混用模型维度
智库投递outbox 幂等写入 ocean_intel 并合并，不覆盖人工审核结果原版文章 ID 与智库文档 ID 可互查；发布成功后才确认投递
问答与地图返回原平台、作者、发布时间、原文链接及证据；地图只使用有证据的位置收录热度不冒充产业规模；引用多篇转载不算多份独立证据

建议处理 worker 持续消费持久化任务，初期模型并发 2，不设每轮 8 篇限制；每篇／每阶段保存进度，超时续跑与指数退避。沿用现有采集发布锁和合并函数，先做增量可靠性，再将整批快照任务迁移到持久队列；这部分是拟开发改造，不是当前已存在的全天候队列。

费用控制采用“内容未变化不重做、先过滤后深加工、失败退避、日用量可见”。即便正文采集无总篇数限制，也需遵守供应商限流与大模型账户额度；模型余额不足时保留原文并暂停加工，不影响其他无需模型的采集。

9. 分阶段落地与回滚

阶段交付成果上线门槛
A：只读联调验证凭据、订阅清单，分别拉取公众号／X 推文／X 长文样本仅测试真实已订阅账号；正文、日期、原链可核对；空列表不伪装通过全文验证
B：采集接管修复 RSS 隐患；迁移映射；账号管理、采集与出错状态可用先选两个公众号、两个 X 账号灰度；旧历史数量与审核结果不变
C：智库贯通版本、outbox、自动处理和溯源展示连通新内容可从订阅列表追到原文、证据和问答；失败可重试
D：全量切换扩大到用户指定账号，定时同步、告警与历史覆盖说明完善至少观察两个实际轮询周期；有真实新增或受控重放验证，不仅检查页面 HTTP 200

切换前导出现有源与文章数量、备份配置和映射；新连接器先写隔离暂存并与旧文章去重。验证后停用失效扫码采集任务，保留旧文章及入口，不执行删除会话／历史数据等无关清理。失败时关闭 Mp2RSS 本地流并保留已取得资料，原有 EIA、官网及 RSS 任务继续运行。不要为了接新源修改现有其他服务的 Nginx location。

10. 验收用例与成功标准

用例必须观察到的结果
凭据正确／无效／到期成功可列出账号；错误不泄露 key，状态准确，失败不会清空旧订阅
同一 X 账号开启两条流一个账号，两套进度；某流无内容不使另一流失败
超过一页的数据公众号及 X 分页各按自身契约完整处理；无固定 8／50 条总量截断
重复轮询、重复投递重复数增加而文章／事件不重复；旧人工审核结果保留
中断与重启从持久化任务继续；上次成功进度不被失败页提前推进
摘要先到、正文后补pending_body 更新成完整新版本，自动进入后续处理
短推文与长线程完整短帖不被文章长度阈值误删；各段引用可定位、作者不串位
转推／引用／外链引用保留被引用者；外链不覆盖原帖；转推不能自动变为“合作”
中文／英文中文不重复翻译；英文完成后显示译文；原文和数字可核对
无关能源资讯明确排除原因；待复核内容不计入海洋主题成果
两库桥接失败文章已保存但智库待投递，恢复后自动补投，无静默丢失
原文修改新版本使旧处理状态失效；历史报告引用版本仍可追溯
安全显示前端响应、日志、报表、页面原链均不包含 Feed 密钥；正文 HTML 经净化
统计口径显示采集量、独立文章、有效事件、完成加工分别计数；订阅起点前无数据不填零
旧功能回归历史公众号、EIA、其他 RSS 与官网内容仍可检索；无源名误合并

新来源入库不应默认“已核验”。抽取引用通过校验后仍是待核验候选；问答须区分机构自述、媒体转述与多源印证。需要展示趋势时，只采用同口径指标或明确标注“当前收录量”，尤其不能用新订阅后的不完整时间窗推断全年行业变化。

11. 用户需要提供什么，哪些无需提供

材料建议提供方式用途
Feed 密钥（优先）在服务器独立受限配置中保存，或后续通过本系统仅写入式密钥表单配置同一账户读取公众号和 X 的订阅及内容；不需要微信 Cookie
付费订阅链接（替代）若只能提供链接，分别给一个公众号、X 推文、X 长文样本；按敏感凭据处理验证 Feed 类型、来源和正文；不自动把“提供链接”视为授权增删远端订阅
目标账号清单公众号名称＋代表文章链接；X @handle＋是否要推文／长文核对主体、排除同名账号，建立旧源映射
X 控制台订阅先在 Mp2RSS 控制台完成目标账号订阅本系统读取已订阅账号，无需提供 X 登录密码
套餐确认信息档位、到期日、订阅建立时间；不需要付款凭证或支付密码容量规划、覆盖起点及续费提醒
真实样本优先选择已经有新内容的账号；长文为空时另选实际发布过长文的样本验证正文、转推、线程与空值；空列表不能替代解析验收

Feed 密钥与链接具有访问能力，完整付费链接不应进入代码仓库、普通业务日志或公开文档。本文所有接口仅使用占位符。首期建议只授权读取已订阅内容，公众号新增／取消功能在用户明确操作时才触发。

现阶段不用购买 X 官方开发者 API 来配合本方案，也不需要恢复公众号扫码作为前置条件；但真实覆盖取决于 Mp2RSS 的收录能力。若后续需要订阅前历史、媒体原件或更低延迟，应作为单独需求向供应商确认，不能用现有套餐名称推定支持。
