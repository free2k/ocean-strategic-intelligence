## 审查范围和方法

审查覆盖管理和智库数据库连接、规则发布、原文及向量处理、根路径 API、Worker 投递、文件和进程锁、启动初始化、后台调度、Cookie、浏览器草稿、供应商订阅及发布恢复脚本。

行为验证直接读取对应源码中的函数或配置表达式，在 Node.js VM 中使用合成配置及内存替身运行。数据库、网络、进程创建和文件写入分别使用替身，不导入应用启动入口，不读取生产环境文件，不调用原站接口。Linux 文件锁分支通过模拟 process.platform=linux 验证，不在开发机或服务器执行 flock。

此外，读取当前代码的哈希并在验证后比较。该检查证明此次验证期间受检查文件没有改变，不代替生产数据库、线上配置或性能状态核验。

## 必须进一步切断的间接影响

### 主机和部署入口

共用主机时，CPU、内存、磁盘、网络及系统服务仍由同一操作系统管理。共用 Nginx 时，配置错误或重载也涉及同一个入口进程。不同数据库或进程不能证明这些资源没有影响。

为满足本次前提，实施方案默认改为独立部署主机、独立 PostgreSQL 实例及存储、独立反向代理及 TLS 私钥。只新增低碳 DNS 记录，不改变原站解析及代理配置。共享主机或共用入口的方案不计入本次严格隔离验收范围。

### 供应商额度及公网出口

不同 API Key 可能仍受同一个账号余额、组织总并发或日限额约束。需要确认独立账号，或取得并核验独立预算、总并发及限制边界。不能仅凭密钥字符串不同宣布隔离。

采集还应使用低碳专属出口和代理，分别限流。若共用被来源按 IP 限制的出口，低碳增量请求可能使原站遭遇限流；仅在本地分开队列不解决这一点。未具备独立账号及额度的渠道暂不启用。

## 实施方案的补强决定

1. 独立主机及入口代理由建议升级为默认必需条件，不重载或修改原站代理。
2. 将模型及采集供应商的独立预算、并发、远端订阅集合和出口列为验收项。
3. Worker 上游和锁根目录必须显式配置，禁止保留原站默认端口及绝对锁路径。
4. 自动任务检查覆盖 Nuxt 插件、systemd、独立 Worker 和智库计时器；手动入口分别核验，不能只检查 INTEL_SCHEDULE。
5. 初始化、恢复、备份及发布工具纳入隔离边界，原站权限及环境不得进入低碳发布包。
6. 增加 ISO13 基础设施隔离和 ISO14 外部额度及出口隔离门槛，和原 ISO01 至 ISO12 一并执行。
