# 调度输入与历史快照清理

## 新任务

PostgreSQL 模式下，任务目录只写 `task-input.json`，记录任务编号和工作库版本。文章及其他数组记录以 `(field, key, hash)` 固定在 `ocean_intel.task_inputs`；不可变正文保存在共享的 `task_objects` 中，相同内容只保存一次。首次启用会建立当前记录的共享缓存，之后各轮复用，不是每轮复制工作库。

读取按最多 20 条分页，并验证内容 SHA-256。各采集入口通过 `readTaskWorkspace` / `saveTaskWorkspace` 访问任务数据；写入只提交哈希或顺序变化的记录，每批最多 20 条或约 2 MB（单条记录可能更大）。任务 generation 防止旧进程覆盖新结果。当前部分采集算法仍在内存中组装文章集合，受独立 worker 资源限额约束；此次取消的是调度的整库临时文件，并非所有算法都已成为单文章常驻内存。

任务成功合并到工作库后删除输入引用和目录标记。失败或进程重启时，删除未变化的基线引用，仅保留变化记录、原版本引用与删除标记。重启清理由获得独占 worker 锁的进程执行。文章模型检查点独立保留，下一轮重用完成的结果。没有引用且不属于当前工作库的共享对象会回收。

`task_objects` 的散列采用 JSON 文本的 SHA-256，不按语义认定两个不同原文相同。失败差异位于 `task_inputs` 与 `task_workspaces(status='failed')`，不能直接将其当作完整工作库发布。

无数据库的开发模式，以及尚未迁移的独立工具，继续使用兼容 `snapshot.json`。线上根目录的兼容快照仍保留一份；它不会复制到新调度的 jobs 目录。

分类后的原文 HTML 按文章版本复用线上已有文件，仅为新版本或缺失的文件生成附件，避免每次分类重新复制所有文章原文。

## 历史快照

`snapshot_archive.py` 将旧文件分块、压缩并按 SHA-256 去重。历史目录只留有序恢复清单，重复数据块共享，独有字节只归档一次。只有 JSON 完整性、源文件稳定性、全部持久化块及清单校验通过才删除原文件。可用 `--restore 清单 --output 新文件` 完整恢复；不覆盖已有文件。

已完成快照归档的旧任务还会核对 HTML/PDF/CSV/JSON 附件。每个任务只保存一份 `artifacts.archive.json`，重复附件共用数据块，避免几十万个重复小文件继续占用磁盘和 inode。单轮附件最多 20000 个；恢复时使用 `--restore artifacts.archive.json --artifact-name 原文件名 --output 新文件`。不处理活动任务、带未完成 `.part` 的目录或未知文件类型。

默认额外保留最近 3 份旧快照；活动任务、未完成发布、24 小时内未验证的文件和 `.part` 未完成文件独立保护，因此不是强制全站只有 3 个历史记录。带原 SHA-256 校验的旧 gzip 可显式使用 `--include-verified-gzip`。

清理单轮最多 30 分钟或 200 个快照，结束休息约 5 分钟再继续。限制为 CPU 25%、内存上限 512 MB、读 8 MB/s、写 2 MB/s，并检查可用内存、系统负载、磁盘空间及内存/IO 压力。短暂资源紧张时先停止读写、原地等待最多 60 秒，恢复后从当前进度继续；持续紧张则延期，保留源文件，下轮安全继续。共享归档块不自动删除，以保护已归档的独有历史。

部署服务：`deploy/ocean-snapshot-dedup.service` 和同名 `.timer`。观察 `journalctl -u ocean-snapshot-dedup.service` 中的 `sourceBytes`、`newBlockBytes` 和延期原因。清理存量是分批后台工作，不应通过一次无限制扫描或删除来加速。
