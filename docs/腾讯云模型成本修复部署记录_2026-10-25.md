## 2. 业务数据如何保证保留

最终切换窗口采用以下保护：

1. 完成 PostgreSQL 完整备份，并用 `pg_restore --list` 验证备份目录可读取。
2. 暂停项目定时器和写入进程，保留当时已提交的数据。
3. 对现有业务表短暂持有写入隔离锁；外部并行采集等待切换完成，读取仍可进行。
4. 比较切换前、替换程序后、服务重启后的业务表、序列、资料文件和原配置。
5. 验证一致后释放隔离锁，恢复调度并启用新 worker。

| 核验范围 | 结果 |
| --- | --- |
| 现有业务表 | **50 张表，行数与可见 MVCC 行版本校验一致**；普通新增、更新或删除会改变该校验 |
| 原有数据库序列 | 一致 |
| 资料文件 | **178,555 个文件，合计 13,542,234,229 字节，SHA-256 校验一致** |
| 原密钥与连接配置 | `.env`、`mp2rss.env`、`processing.env` 内容哈希一致 |

资料文件覆盖正式数据目录、证据原始文件目录和原发布目录的共享数据。对已完整计算 SHA-256、且设备、inode、大小、修改时间和变更时间均未变化的文件复用校验值；发生变化的文件重新读取计算，以缩短停机时间。

## 3. 仅增加必要的任务存储结构

新增：

- `model_ops.requests`：模型请求缓存和回执。
- `model_ops.batches`：Batch 提交和结果回收记录。
- `model_ops.resources`：用户请求的全文翻译和识图任务。
- `classification.semantic_queue.receipt_id`：可空字段，用于关联回执。

没有为这些结构重写既有业务行，没有删除或重建旧表。原有数据目录留在原位，新发布目录继续引用原有数据。

还启用了 `INTEL_PRESERVE_STARTUP_DATA=true`：网站重启加载已保存资料时不回写工作区元数据，处理服务启动时不清理既有任务缓存。显式导入、正常采集和后续用户操作仍按业务流程执行；任务缓存整理需要另行安排。
